= Lab Guide: Run Signed Collections from Automation Controller

_A capstone exercise: run a playbook that uses a signed collection from a signature-validated project._

---

[discrete]
====
*Estimated time to complete: 10 minutes*
====

In the previous modules, you signed an Ansible project locally (Modules 2-5) and signed collections server-side in Private Automation Hub (Modules 6-8). In this final module, you will tie everything together by running a playbook from Automation Controller that uses a module from a signed collection -- all within a signature-validated project.

The module setup installed `ansible.test_collection` (signed and approved in Module 7) directly into the project and re-signed it with `ansible-sign`. This means Controller validates the integrity of the entire project -- including the embedded collection -- when it syncs from git.

== Task 1: Sync the Signed Project

The module setup has added a new playbook and the signed `ansible.test_collection` to the `ansible-sign-demo` repository, then re-signed the project. You can verify the new files in the `Terminal` tab:

[source,bash]
----
cat ~/ansible-sign-demo/playbooks/use_signed_collection.yml
----

[source,bash]
----
ls ~/ansible-sign-demo/playbooks/collections/ansible_collections/ansible/test_collection/
----

Now go to the `Automation-Controller` tab and log in if needed.

====

* **Username:** `admin`
* **Password:** `ansible123!`

Navigate to **Automation Execution** -> **Projects**, and click the **Sync** button (the icon with two circling arrows) on the **Signed Project**.

Watch the **Jobs** view for the sync to complete. It should succeed because the project signature is valid -- signed with the GPG key from Module 2 and validated by the credential from Module 3.

You can verify the sync succeeded by clicking on the job and looking for:

[source,text]

TASK [Verify project content using GPG signature] ******************************

== Task 4: Launch the Job

Click the **Launch** button on the job template. This will:

1. Use the **Signed Project** (signature-validated from git)
2. Run the playbook that calls the `hello_world` module from `ansible.test_collection`

Watch the job output. You should see:

[source,text]
----
TASK [Call hello_world from ansible.test_collection] ***************************
ok: [localhost] => {
    "changed": false,
    "msg": "Hello, AAP Controller! This module is from the signed ansible.test_collection."
}

TASK [Show the result] ********************************************************
ok: [localhost] => {
    "result.msg": "Hello, AAP Controller! This module is from the signed ansible.test_collection."
}
----

A successful job proves the full end-to-end chain:

* The collection was signed server-side by Private Automation Hub (Module 7)
* The signed collection was embedded in the project and the project was re-signed with `ansible-sign`
* Controller validated the project signature on sync -- covering the playbook, the collection, and all other project files
* The playbook executed a module from the signed collection

== Going Further: Organization Galaxy Credentials and `requirements.yml`

In this lab, you embedded the signed collection in git and relied on *project-level* Content Signature Validation to cover it. In production, organizations more often pull collections from Private Automation Hub at project sync time.

The organization-scale control for that is not a GPG field on the organization. Organizations use **Galaxy credentials** (`Ansible Galaxy/Automation Hub API Token`) to decide which content servers projects may install from. Project-level **Content Signature Validation Credential** (the GPG Public Key you used in Module 3) still only validates *project* signatures.

This optional path shows that org-scoped Galaxy credential pattern end to end.

=== Step 1: Get a Private Automation Hub API Token

In the `Terminal` tab, read the token already written into your Galaxy config:

[source,bash]
----
awk -F= '/^token=/{print $2; exit}' ~/ansible.cfg
----

If that is empty, create a new token:

[source,bash]
----
curl -sk -u admin:ansible123! -X POST https://localhost/api/galaxy/v3/auth/token/ | jq -r .token
----

Copy the token value. You will paste it into Controller next.

=== Step 2: Create an Ansible Galaxy / Automation Hub Credential

Go to the `Automation-Controller` tab. Navigate to **Automation Execution** -> **Infrastructure** -> **Credentials** and click **Create credential**:

[cols="1,2a"]
|===
| Parameter | Value
| Name | `Private Automation Hub — Published`
| Organization | `Default`
| Credential Type | `Ansible Galaxy/Automation Hub API Token`
| Galaxy Server URL | `https://localhost/api/galaxy/content/published/`
| API Token | The token from Step 1
|===

Leave **Auth Server URL** blank. Click **Create Credential**.

=== Step 3: Attach the Credential to the Organization

Galaxy credentials are attached at the *Organization* level. Every project in that organization uses this ordered list when installing collections from `collections/requirements.yml`.

Navigate to **Access Management** -> **Organizations**, open **Default**, and click **Edit organization**.

In **Galaxy credentials**, add `Private Automation Hub — Published` and place it **first** in the list (order sets precedence). Click **Save**.

=== Step 4: Allow Self-Signed TLS for Galaxy Downloads

This lab uses a self-signed certificate on the platform gateway. Navigate to **Settings** -> **Job settings** and enable **Ignore Ansible Galaxy SSL Certificate Verification**, then save.

Without that setting, project syncs that install collections from `https://localhost` may fail TLS verification.

=== Step 5: Create a Project That Pulls Collections from the Hub

Create a small project that declares the signed collection in `requirements.yml` instead of committing collection files to git:

[source,bash]
----
mkdir -p ~/hub-collections-demo/{playbooks,collections}
cat << 'EOF' > ~/hub-collections-demo/collections/requirements.yml
---
collections:
  - name: ansible.test_collection
    version: 1.0.0
EOF
cat << 'EOF' > ~/hub-collections-demo/playbooks/use_hub_collection.yml
---
- name: Use a collection installed from Private Automation Hub
  hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Call hello_world from ansible.test_collection
      ansible.test_collection.hello_world:
        name: "PAH via requirements.yml"
      register: result

    - name: Show the result
      ansible.builtin.debug:
        var: result.msg
EOF
----

In the `Gitea` tab, create a new repository named `hub-collections-demo` under the `student` account (leave it empty -- do not initialize with a README). Then push from the terminal:

[source,bash]
----
cd ~/hub-collections-demo
git init
git add collections/requirements.yml playbooks/use_hub_collection.yml
git commit -m "Pull signed collection from PAH via requirements.yml"
git remote add origin http://gitea:3000/student/hub-collections-demo.git
git push -u origin HEAD
----

Use Gitea username `gitea` and password `gitea` if prompted.

=== Step 6: Create and Sync the Project in Controller

In Controller, navigate to **Automation Execution** -> **Projects** and click **Create project**:

[cols="1,2a"]
|===
| Parameter | Value
| Name | `Hub Collections Project`
| Organization | `Default`
| Source Control Type | `Git`
| Source Control URL | `http://gitea:3000/student/hub-collections-demo.git`
| Content Signature Validation Credential | Leave empty for this exercise
|===

Click **Create project**. The sync should succeed and, because of the org Galaxy credential, install `ansible.test_collection` from Private Automation Hub.

Open the project update job and look for the collection install task. You should see Controller run something equivalent to `ansible-galaxy collection install` against your hub.

NOTE: Leave **Content Signature Validation Credential** empty here on purpose. That field is for project signing (`ansible-sign`), which you already practiced on **Signed Project**. This exercise is only about org Galaxy credentials and hub-sourced collections.

Create a job template (you can reuse `Module 09 Inventory`):

[cols="1,2a"]
|===
| Parameter | Value
| Name | `Hub Collection Demo`
| Project | `Hub Collections Project`
| Inventory | `Module 09 Inventory`

=== How the Trust Boundaries Differ

[cols="1,1"]
|===
| **This lab (embedded collection)** | **Org Galaxy credential approach**

| Collection files committed into the git project
| Collection pulled from PAH at sync time via `collections/requirements.yml`

| Org does not need a PAH Galaxy credential for the collection
| Organization Galaxy credential controls which hub/Galaxy servers may supply content

| Project Content Signature Validation covers playbooks *and* embedded collection files
| Project signature (if used) covers playbooks and `requirements.yml`; PAH is the source of truth for the collection artifact

| Uses your personal GPG key on the project (Module 2/3)
| Uses an `Ansible Galaxy/Automation Hub API Token` on the organization

| Collection GPG verification shown on the CLI in Module 8 (`--keyring`)
| Collection GPG verification is still a client/keyring concern; Controller's org-level control is *which content server* is trusted
|===

The Galaxy-credential approach is what most production Controller setups use: keep playbooks in git, keep collections in Private Automation Hub, and scope hub access per organization. Combine it with project signing when you also want `ansible-sign` protection on the repository that declares those dependencies.

== Conclusion

This lab has covered the complete content signing story in Ansible Automation Platform:

* **Project signing** (Modules 2-5): You used `ansible-sign` to sign Ansible projects locally with your own GPG key. Automation Controller validated those signatures when syncing projects from source control.
* **Collection signing** (Modules 6-8): You published collections to Private Automation Hub, which signed them server-side using its own signing service. You verified those signatures on the client side using `ansible-galaxy` with a GPG keyring.
* **End-to-end execution** (Module 9): You ran a playbook from Controller that uses a module from a signed collection -- all within a signature-validated project. The collection's integrity was established by PAH, and the project's integrity was validated by Controller.
* **Organization Galaxy credentials** (Going Further): You configured an `Ansible Galaxy/Automation Hub API Token` on the organization so Controller could install signed collections from PAH via `requirements.yml` -- the production-oriented alternative to embedding collections in git.

Together, these mechanisms provide end-to-end content integrity for Ansible automation -- from the projects that define your automation workflows to the reusable collections they depend on.
